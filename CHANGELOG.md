## 2026.09.10.1655

- Narrowed the Elastic category filter to the categories the widget actually selected instead of replacing them with the raw aggregation buckets (#2923). The aggregation is declared `use-filter`, so it is scoped to the matched documents — but a document carries **every** category it holds, not only the ones the widget selected. On San Rafael mini beta's `/major-development-projects-news/`, 9 of the 52 posts matching that widget's 26 categories are also tagged Homelessness, so `Homelessness (10)` came back as a bucket and `form_filled_fields()` handed the buckets straight to `#options`, discarding the restricted list `build_filters()` had already produced. Three more leaked on that one page: City News (19), Merrydale short-term shelter (1), Community and Economic Development (1). New `TeaserFilterTerms::narrow_to_allowed()` intersects the two; both sides have been keyed by slug since #2720, so it is a straight key intersection that preserves the Elastic doc counts and the aggregation's ordering. An empty intersection returns `[]` deliberately — every caller guards with `if (! empty($options))`, so the fallback is the widget's own configured list and **never** the unrestricted buckets. That also covers the version-skew case: against a `wp-proud-core` from before #2720, `#options` is term_id-keyed, nothing intersects, and the filter degrades to the configured list without Elastic counts rather than leaking.
- Stopped `query_alter()` overwriting the widget's `tax_query` with the visitor's selection (#2923, PCD379). It now ANDs the visitor's clause onto the restriction `TeaserList` has already placed there. `wp-proud-core`'s `process_post()` has the matching change; both are required, because with Elastic running this path is what builds the query, so fixing only core would have left the reported configuration broken. Selecting the leaked `Homelessness` returned 57 posts against the mini beta data where 10 are in scope.
- **Not a #2720 regression, checked deliberately.** `git log -L` over the block shows the replace behaviour predates it; #2720 changed only the keying and the aggregation size. The size is not implicated either — this widget's aggregation returns 22 buckets, far below both the old fixed `size => 100` and the computed size that replaced it. Enabling Elastic exposed a defect that was already there.
- 8 new tests in `tests/NarrowToAllowedTest.php` built from the real reported page's data; suite 63 tests / 75 assertions, up from 55.
- **Ships with wp-proud-core 2026.09.10.1653 or later and must not be split from it.**
- Elasticsearch is not reachable from a local install, so the aggregation half is covered by unit tests over bucket fixtures and by reconstructing the buckets from the real database. The nested `relation => AND` `tax_query` needs confirming against a live index on mini beta after deploy.

## 2026.09.09.1239

- Fixed the teaser category filter hiding categories outright on any site with more than 100 terms, and moved the filter off term names and onto term slugs. Reported against San Rafael, where filtering `/news/` by Public Works disagreed with the admin. `query_alter()` asked Elasticsearch for the category facet with a hard-coded `'size' => 100`, and `form_filled_fields()` then **replaced** the checkbox options with whatever came back. A terms aggregation returns only the top N buckets by `doc_count` and discards the rest silently, so San Rafael's 104 category buckets rendered as exactly 100 checkboxes and four categories with published content — Police Department (3 posts), Public Safety Center (1), Southeast San Rafael Specific Plan (1), Terra Linda Mural (1) — had no way to be selected at all. Their content stayed indexed and searchable, which is why resyncing never helped. San Rafael is the only site over the cap today; bucket counts across the cluster are San Rafael 104, minibeta 83, beta 37, Santa Ana 35, Petaluma 20, Somerville 9, and any site that grows past 100 categories inherits this. The size now comes from `wp_count_terms()` plus 25 of headroom, floored at the historical 100 so no site can regress, ceilinged at 1000, and filterable through `proud_teaser_elastic_agg_size`; the result is clamped to 1–65536 afterwards so a filter cannot produce a request Elasticsearch rejects or, worse, a `size: 0` that empties the facet entirely. **The reported symptom was not the Public Works count.** That part is not a bug: `wp_term_taxonomy.count` is non-hierarchical (396) while `category_name=` in `WP_Query` and ElasticPress's ancestor indexing both are (453). Comparing the two 453-result sets post ID by post ID gives zero differences in either direction, so Elastic and the admin already agreed exactly. Public Works has 40+ children — Everything Traffic 278, Maintenance Divisions 270, Permitting News 241 — which is what makes the two numbers look like a discrepancy. **Second change, same release: the facet now aggregates and matches on `terms.<taxonomy>.slug` rather than `terms.<taxonomy>.name.raw`.** Names are stored HTML-encoded, so the old code had to keep an `htmlentities()` on the query side in sync with an `html_entity_decode()` on the facet side — querying the live index for `Arts & Culture` returns 0 while `Arts &amp; Culture` returns 26. The two halves cancelled out by coincidence, and any change to either would have broken a subset of categories rather than the whole filter, which is the "some filters" in the issue title. `htmlspecialchars()` replaces `htmlentities()` in the one place a name lookup is still needed, because `htmlentities()` also converts non-ASCII to named entities and would look up a category named "Café" as "Caf&eacute;". No reindex is required — `terms.category.slug` and `terms.category.term_id` are already in the live mapping, both returning 453 for Public Works. **This also closes a pre-existing stored XSS, which is the strongest argument for the slug switch.** `templates/option-box.php` in wp-proud-core echoes `$id` and `$name` without escaping, and `proud-form.php:542` builds them by interpolating the `#options` key — which was an administrator-authored term name on this path. `pre_term_name` runs `sanitize_text_field` + `wp_filter_kses` + `_wp_specialchars` with `ENT_NOQUOTES`, so it strips tags but passes double quotes through verbatim: `apply_filters('pre_term_name', 'Arts" onmouseover=alert(1) x="')` returns the payload intact. Anyone holding `manage_categories` — Editor on ProudCity — could therefore name a category so that script executed for every anonymous visitor on a listing whose facet included that term. Slugs are confined to `[a-z0-9_-]` by `sanitize_title()`, so the attribute halves are now safe by construction rather than by escaping. `options_from_buckets()` keys on the **resolved** `$term->slug` rather than the raw bucket key, because the lookup is not an equality check — `WP_Term_Query` sanitises with `sanitize_title()` before querying, so a bucket key of `news<img src=x>` matches the term slugged `news` while the raw key would land in the attributes; reaching that needs control of the Elasticsearch response, but it is exactly the bug class being closed. Labels are escaped here because the template does not escape them; note that if `esc_html()` is ever added to `$text` in `option-box.php`, the `esc_html()` in `options_from_buckets()` must be removed in the same commit or every category name containing `&` double-encodes sitewide. `options_by_slug()` covers the no-aggregation branch and is idempotent — a naive `(int)` cast of an already-slug key gives 0 and would drop every option — and it keeps an option it cannot resolve rather than dropping it, because the caller replaces `#options` wholesale whenever the result is non-empty, so dropping meant one key that happened to resolve could collapse the whole filter to a single checkbox. Both resolvers try the **slug before the term ID**, because WordPress permits a fully numeric slug and this database already contains two same-taxonomy collisions (`faq-tags` slug `911` versus term ID 911 "library", slug `1099` versus ID 1099 "carshare"); `311`, `911` and bare years are ordinary category names for a city. `$form_taxonomies` carries the taxonomy from `query_alter()` to `form_filled_fields()`, which only receives a form id; because `form_id_base` is the shared `TeaserList::_FORM_ID` constant, two teaser lists of different post types on one page record a conflict as unknown and are left alone rather than being rekeyed against each other's taxonomy — "public-works" exists in five taxonomies on San Rafael. **This release cannot ship without wp-proud-core 2026.09.09.1247 or later.** The two plugins are pinned independently in the site template, and `\Proud\Core\resolve_taxonomy_filter_slugs()` lives in core; `TeaserFilterTerms::resolve_slugs()` guards the call with `function_exists()` so a skew degrades to an unfiltered `tax_query` instead of a fatal on every filtered teaser query, but that is a seatbelt and not a substitute for bumping both pins in the same revision. Old `?filter_categories[]=Public+Works` links, the term-ID links `contact-submenu-widget.class.php:78` builds, and the new slug links all resolve to the same results. First test suite for this plugin: 55 tests across `AggregationSizeTest`, `FilterOptionsFromBucketsTest`, `OptionsBySlugTest` and `ResolveSlugsBridgeTest`, with `lib/teaser-filter-terms.php` deliberately free of any load-time dependency because `lib/elasticsearch.class.php` requires the whole of ElasticPress on line 11 and cannot be loaded in a test. Verified against production rather than fixtures: all 120 San Rafael category rows resolve from their slug, stored name, decoded name and term ID (480 probes, 0 misses), the four ampersand categories included — `Library & Recreation` resolves to `libraryrecreation`, which `sanitize_title()` would never produce, proving a real term match rather than the fallback. Security review returned 0 Critical and 0 High open.
